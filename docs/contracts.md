# Контракты подсистем и расширений

Статус: draft, версия контракта `0.1`. Нормативные правила этого документа важнее иллюстративных названий методов. Java-сигнатуры появятся после исследования первого адаптера. Сейчас исходники содержат только описание пакетов.

## 1. Жизненный цикл расширения

Планируемые сущности: `ExtensionDescriptor`, `ExtensionContext`, `CapabilityRequest`, `Diagnostic`.

Порядок: discover → validate → negotiate → initialize → active → quiesce → dispose. Это модель будущего runtime, не реализованная машина состояний.

- Descriptor содержит namespaced ID, версию, диапазон Foundation API, обязательные и необязательные зависимости, capabilities, точки расширения и конфликты.
- Все обязательные требования и циклы зависимостей проверяются до создания GPU-работы расширения. Нельзя добавить обязательный device feature после создания устройства.
- Инициализация получает только объявленные сервисы. Самостоятельная глобальная регистрация из static initializer не входит в контракт.
- Остановка прекращает новые задачи, дожидается ранее отправленной работы и освобождает ресурсы владельца.
- Сбой одного Java-расширения не считается изолированным от процесса. Hot reload произвольных модов и sandbox не обещаются.

Ванильный Lua-мод не обязан иметь этот descriptor: его жизненным циклом продолжает управлять PZ.

## 2. Граница игры и представления

Планируемые сущности: `WorldEpoch`, `FrameId`, `VisualSnapshot`, `ViewDescription`, `VisualObjectId`, `ResourceDelta`, `UiCommandList`.

| Поле | Смысл |
|---|---|
| epoch | Новое значение после смены или повторной загрузки мира |
| frame | Монотонный номер опубликованного визуального кадра внутри эпохи |
| simulationTick | Игровой tick, из которого взяты данные; не GPU-время |
| interpolation | Согласованный коэффициент между игровыми состояниями |
| views | Камера и область вывода каждого вида/локального игрока |
| resources | Объявленные изменения постоянных визуальных ресурсов |
| draw/UI data | Согласованные данные рисования и порядок UI |

Снимок не содержит изменяемых объектов PZ. Опубликованные диапазоны CPU-памяти нельзя повторно использовать до завершения их потребителя. Смена мира исключает обращение к данным прежней эпохи. Момент игровых callbacks и их аргументы сохраняет адаптер.

## 3. Владение ресурсами

Планируемые сущности: `ImageHandle`, `BufferHandle`, `SamplerHandle`, `PipelineHandle`, `ResourceOwner`, `ResourceLease`.

Handle типизирован, принадлежит устройству и содержит поколение; произвольное число GL texture ID не является handle Foundation. Descriptors определяют формат, размер, usage, число samples, слои и цветовое пространство. При несоответствии usage ошибка обнаруживается до исполнения задачи.

| Ресурс | Владелец | Условия доступа |
|---|---|---|
| Постоянный | Runtime или конкретное расширение | Явное создание и завершение использования |
| Временный | Runtime кадра | Только объявленные задачи кадра |
| Заимствованный | Другой владелец | Lease с диапазоном и сроком действия |
| Внешний/native | Согласованный внешний владелец | Явные начальное/конечное состояние и completion |

Логическое уничтожение и физическое освобождение разделены. GPU-память освобождается после завершения всей использующей её работы. Resize создаёт новые поколения зависимых изображений. Ошибка включает owner, resource ID и задачу. Мод не уничтожает чужие ресурсы.

## 4. Граф задач и порядок

Планируемые сущности: `TaskGraph`, `GraphicsTask`, `ComputeTask`, `TransferTask`, `ResourceAccess`, `CompletionToken`.

Каждая задача объявляет чтения и записи конкретных диапазонов буфера или подресурсов изображения. Для imported resources задаются внешние ожидания, начальные и конечные состояния. Проверяются циклы, конфликтующие записи, чтение отсутствующего результата и срок handle. Запись с явным порядком допустима; неоднозначная гонка — ошибка.

Граф сохраняет отдельные ограничения визуального порядка: прозрачность, stencil, ванильные callbacks и порядок UI. `before/after` уточняют семантическое подключение, но не заменяют зависимости ресурсов. Побочные действия игровой логики не выполняются из GPU-задач.

Runtime владеет submit, presentation и общей синхронизацией. Завершение задачи не обязательно означает завершение GPU. Readback возвращает асинхронный результат; синхронная остановка GPU не является неявным поведением API.

## 5. Точки расширения presentation

Начальные семантические имена: `scene.prepare`, `world.opaque`, `world.transparent`, `world.composite`, `ui.compose`, `frame.capture`. Окончательный набор подтверждается инвентаризацией PZ.

Кроме GPU-задач расширения могут регистрировать источники визуальных объектов, material providers, загрузчики собственных форматов, камеры, offscreen targets, UI-компоненты и диагностические данные. Загрузчики namespaced и не перехватывают ванильный формат без явной замены.

Контракт точки задаёт доступные ресурсы, координаты, alpha, depth/stencil, цветовое пространство, timing и область локального игрока. Добавление работы и замена стадии — разные операции. Замена требует эксклюзивного provider либо явно согласованной композиции. При конфликте выдаётся диагностика до запуска, а не правило «последний загруженный победил».

Пример поведения: мод читает world depth, выполняет compute, затем использует свой буфер при композиции. Второй мод добавляет превью предмета отдельной камерой. Они не делят неявный framebuffer и не перезаписывают глобальные GL states.

## 6. Низкоуровневый Vulkan-доступ

Interop находится в отдельном модуле `graphics-vulkan-interop`. Его будущие Vulkan-типы не экспортируются переносимым API. Подключение явно делает мод Vulkan-зависимым.

Мод может получить ограниченный native recording scope: заимствованный command buffer, разрешённые ресурсы и capabilities устройства. Он обязан объявить работу графу, соблюдать границы scope и сообщить требуемые состояния. Мод не вызывает submit/present и не сохраняет command buffer после scope. Vulkan не гарантирует изоляцию ошибочного native-мода.

Независимые очереди и внешний submit — отложенный контракт с явными ownership transfers и сигналами завершения. Частично исполненная работа не откатывается в OpenGL.

## 7. Capabilities и шейдеры

Согласуются версия API, обязательные features, лимиты, форматы и операции presentation. Базовый профиль устройств утвердим по лабораторным измерениям. Vulkan 1.4 у KosmicKrisp не делает каждое расширение автоматически доступным.

Единый shader pipeline производит SPIR-V, отражает bindings и проверяет согласованность layout. Пространства имён параметров и наборы вариантов принадлежат материалам. Кеш имеет ключи драйвера, GPU, версии shader toolchain, исходного содержимого и специализаций. Не распространяем один pipeline cache между несовместимыми конфигурациями.

## 8. Эволюция API

Версии контрактов и совместимость с билдом PZ — разные оси. Для draft API допустимы изменения с записью в ADR и примечаниями миграции. Стабилизация требует минимум двух независимых клиентов API, включая пример native-доступа. Приватные helpers адаптера не становятся обещанным SDK по факту доступности из Java.
